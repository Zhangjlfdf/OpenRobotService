# AiTaskPlatform 离线评测

把判官（自评）的**行为**变成可复跑的观测，而不是每次靠人看一遍。

## 为什么要有它，以及它刻意不量什么

1. **单跑一次 pass/fail 不构成结论。** 同一输入在 `deepseek-v4-flash` + `temperature=0` 下
   实测能给出完全相反的判定（同一案例 6/6 不通过 ↔ 0/8 不通过）。所以要看**多轮一致率**，
   并把**翻转的用例**点名列出来。
2. **讨论场景不该有固定的通过/不通过标准。** 标准取决于用户问的是什么，同一份回答在不同
   提问下对错不同。实测证据：把判据换回诊断口径、甚至把护栏 `_JUDGE_RULES` 整个抽掉，
   手写的「陷阱」用例**照样全部通过**；专门构造「证据塞 8 条无关话题 + 草稿只答一句」的
   极端输入也全判通过。**固定的「期望通过/不通过」标签是错的工具，已删除**，
   免得后人拿一把没有区分力的尺子当验收。
3. 所以只量两件与「具体问了什么」无关、能客观量的事：**判定稳定性** + **评审意见的落点**。
   落点这一步**用 prompt 复核**（`Evaluator.verify_issues`），不做字符串匹配——评审意见是
   中文散文，机械比对量出来的是「用词像不像」不是「有没有落点」（实测：换词复述材料内容
   会被算成没落点，常用词又会凑出假重叠，最后 20 条意见一条都核对不上）。

**不量**：判得对不对。这不是偷懒，是承认标准随提问变（见第 2 条）。

## 怎么跑

```bash
# 看有哪些用例（不跑，不连网）
python -m ai.agents.AiTaskPlatform.eval.run_eval --list

# 全量跑 3 轮
python -m ai.agents.AiTaskPlatform.eval.run_eval --dataset evaluator_verdicts --rounds 3

# 只跑某几条（id 精确或前缀匹配），多跑几轮看稳定性
python -m ai.agents.AiTaskPlatform.eval.run_eval --only discuss-contradicts,discuss-invents --rounds 5

# 落明细，给复盘用
python -m ai.agents.AiTaskPlatform.eval.run_eval --rounds 3 --json /tmp/eval.json

# 当门槛用（CI 里可选）
python -m ai.agents.AiTaskPlatform.eval.run_eval --rounds 3 --fail-under-consistency 0.9 --fail-under-grounded-rate 0.9
```

退出码：`0` 正常 / `1` 未达 `--fail-under-*` 门槛 / `2` 用法或数据集错误。

**要求**：能调到 LLM（读 `ai/.env`）。**不需要**数据库、不需要 AI 服务在跑——用例集是随仓提交的
JSON。指标层（[metrics.py](metrics.py)）是纯函数，单测不需要网络：
`python -m pytest ai/agents/AiTaskPlatform/eval/test_metrics.py -q`。

## 指标怎么读

```
用例 12 条 × 2 轮 = 24 次判定

判定分布（只是分布，不是对错）  通过 12 / 不通过 12 / 未解析 0
多轮一致率          12/12 = 100.0%

评审意见落点（prompt 复核）  20/20 = 100.0%
  ⚠️ 有 1 轮复核没跑成（调用/解析失败）——不算「没问题」
  ❓ 复核认为「指的东西材料里没有」的意见（可疑：可能在套别的场景模板）——
     [discuss-x 第1轮] 回答没有提到『电机编码器故障』这一根因
        复核说明：材料中没有任何地方提到『电机编码器故障』这一根因。
```

- **一致率 < 100% 时先看翻转清单**：它说明这类输入下判得不稳，而不是模型「偶尔手滑」。
- **落点不是判决**：`grounded=false` 只说明「这条意见引用的具体东西在本次材料里找不到」，
  该不该据此改判据由人决定。`复核没跑成` 的轮次单独列出，**不算「没问题」**。
- 「判定分布」只是分布，不解读成好坏；一份回答该通过还是不通过取决于用户问了什么。

## 复核器有区分力吗（实测，别替它打包票）

有，但边界要写清楚。2026-10-12 用同一份材料喂 3 条意见：

| 意见 | 复核结果 | 是否合理 |
|---|---|---|
| 「证据已定位为单个充电桩硬件问题，回答却说可能是标定漂移」 | `grounded=true` | ✅ 指的是材料里真实存在的内容 |
| 「回答没有提到『电机编码器故障』这一根因」 | `grounded=false`<br>（理由：材料中没有任何地方提到） | ✅ 准确抓出「引用了不存在的东西」 |
| 「回答没有覆盖证据里提到的全部讨论内容」 | `grounded=true` | ⚠️ 落点成立（讨论内容确实在材料里），但**在讨论场景这种要求本身过严** |

第三条就是边界：**落点检查抓「引用了不存在的东西」，抓不到「引用了存在的东西但要求不合理」**。
后者靠判据本身管（见 [../issues.md](../issues.md) #1–#3）。别把落点率当成质量分。

## 加用例

往 `datasets/<名字>.json` 的 `cases` 里加一条：

```json
{
  "case_id": "discuss-<说清场景>",
  "mode": "discuss",              // discuss | diagnose —— 决定用哪套判据
  "context": "工单 #… 用户问：…",
  "evidence": "模型生成时看得到的事实来源（讨论史/附件/检索/记忆）",
  "draft": "待评的回答",
  "why": "这条用例想看什么（哪种错法 / 哪个陷阱）"
}
```

规矩：

- **不写「期望通过/不通过」**——见上面的第 2 条；
- **写明 `why`**：说明这条用例想看什么，供人回原文核对；
- **只用合成数据**，不要抄真实工单/用户信息（占位名如 `工程师A`，工单号如 `#10001`）；
- 新用例类型（另一种 `kind`）= 在 [run_eval.py](run_eval.py) 里加一个执行器 +
  在 `RUNNERS` 登记一行，数据集里用 `kind` 指过来。

## 已知边界

- **不是单元测试**：要真实 LLM，慢且会飘，不要塞进 `pytest` 默认收集范围（本目录只有
  `test_metrics.py` 是单测；复核链路的单测在 `capabilities/core/test_evaluator_verify.py`，
  用假 LLM）。
- **不是全量质量评估**：只覆盖自评判定（`kind=evaluator`）。能力调度质量（监督者 plan 该派谁）、
  日志分析结论质量还没进数据集——需要各自先有 ground truth 或可核对的落点定义。
- **样本量小**：12 条用例。它够用来说「没发现明显问题 + 哪几条不稳」，不够用来说
  「准确率是多少」；**别把 100% 当精度读**。
- **回归网的效力未被证明**：目前没有证据表明这份用例集能区分判据修复前后（见「为什么」第 2 条）。
  要真做回归网，得从生产日志里捞**真实的 evidence/draft 对 + 当时的判定**来建，手写的不算。
